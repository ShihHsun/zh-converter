WHY

繁簡轉換，不只是「換字形」

字形轉換只是第一步

头发→頭髮
吃面→吃麵
那只猫→那隻貓

同一個簡體字，可能對應好幾個繁體字，要看上下文才知道是哪一個。

兩岸用語也不一樣

打印机→印表機
出租车→計程車
土豆→馬鈴薯

台灣的「土豆」是花生。字都對，意思卻錯了，所以必須連用語一起轉換。

FEATURES

我們做了什麼

文

文字轉換

貼上文字，一鍵轉換，可以對調方向，也能複製結果。

檔

字幕檔轉換

上傳 .srt／.txt（最大 1MB），直接下載轉換好的檔案。

碼

自動判斷編碼

UTF-8、UTF-16、Big5、GBK 都看得懂，輸出一律是 UTF-8，不會出現亂碼。

修

修正規則

針對字典已知會轉錯的寫法，在轉換後再修正一次。

  • node --test：用內建的測試執行器，不另外裝套件

CORE

轉換核心：兩段式轉換

輸入文字这颗梨子干你什么事
→
① opencc 字典這顆梨子幹你什麼事
→
② 修正規則這顆梨子干你什麼事
// converterService.js：方向的唯一來源
const DIRECTIONS = {
  'cn-to-tw': { from: 'cn',  to: 'twp' },
  'tw-to-cn': { from: 'twp', to: 'cn' },
};

// 啟動時建立轉換器並快取起來
converters[key] = (text) =>
  fixRules(baseConverter(text));

設計重點

  • 建立轉換器成本較高，所以啟動時先建好並重複使用
  • 在 DIRECTIONS 新增一個方向，驗證和 /directions 會自動跟著更新
  • 修正規則越長的優先，所以可以用左右相同的規則保護正確用法，例如「预设立场」

LESSON LEARNED

修正規則的取捨：「於小姐」事件

我們原本想這樣修姓氏…

于小姐→於小姐（字典轉錯）

於是加了規則：於小姐 → 于小姐

結果 code review 時發現…

屬於小姐→ 屬于小姐 ✗
由於先生→ 由于先生 ✗
模範先生→ 模范先生 ✗

最後的決定

  • 常見詞比姓氏常出現得多，而且列舉不完
  • 所以移除姓氏規則，改寫進 docs/known-limitations.md
  • 補上測試，防止以後的規則再誤改這些詞
  • 原則：新增規則前，先想想這個寫法會不會出現在其他正確的詞裡

💡 寧可少修一個字，也不要誤傷一百個詞。

FILE ENCODING

上傳的檔案是什麼編碼？

1
開頭是 UTF-16 BOM（FF FE／FE FF）嗎？
→ UTF-16
2
能用 UTF-8 嚴格解碼（fatal）嗎？有沒有 BOM 都可以
→ UTF-8
3
位元組範圍評分：Big5 的證據比 GBK 多嗎？
→ Big5
4
以上都不是
→ GB18030

為什麼一定要先判斷 Big5？

GB18030 幾乎能解碼任何位元組，Big5 檔案用它解碼不會報錯，只會變成亂碼。

  • Big5 證據：前導位元組 A4–AF，或後導位元組 40–7E
  • GBK 證據：前導位元組 C9–F7
  • 平手時用 GB18030

SUBTITLES

字幕檔：只轉換文字，不動時間軸

// 上傳：影片.srt（GBK 編碼）
1
00:00:01,000 --> 00:00:03,500
我的电脑内存不够了

2
00:00:04,000 --> 00:00:06,000
去买个方便面吧
// 下載：影片-繁體.srt（UTF-8）
1
00:00:01,000 --> 00:00:03,500
我的電腦記憶體不夠了

2
00:00:04,000 --> 00:00:06,000
去買個泡麵吧

序號行、時間軸行用正規表示式辨識，原樣保留

檔名會清掉不安全的字元，再加上 -繁體／-簡體
